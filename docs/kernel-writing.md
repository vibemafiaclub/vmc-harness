# 커널 문서 작성 원칙 (spec 01 P6)

대상: 커널 문구 전부. `engine/vmc_harness/PRINCIPLES.md`, 게이트 메시지(`core/inject.message`로 나가는 모든 문구), 하네스가 LLM에 주는 지시문(진단·PM·과설계 판정·학습 후보 추출·클렌징 후보·렌더링·게이트 생성).

## 쓰는 것

- **사실**: 지금 어떤 상태인가. 무엇이 있고 무엇이 없나(경로·명령·숫자는 그대로)
- **제약**: 하면 안 되는 것, 넘으면 안 되는 선(안전선·출력 형식·시간·토큰 상한)
- **목표**: 무엇을 얻으려는가
- LLM 지시문은 여기에 **참고할 수 있는 것**(자료·도구 — 쓸지 말지는 모델이 정한다)과 **출력 형식**을 더한다

## 쓰지 않는 것

- 절차: "1단계 … 2단계 …", "먼저 X를 하고 그다음 Y" 같은 일하는 순서. 방법은 도구로 쥐여 준다
- 게이트 메시지 안의 해결 방법 지시: 게이트 메시지는 **무엇이 빠졌는지·무엇을 어겼는지만** 담는다
  - 예(맞음): `완료 게이트: be/api/orders.py가 바뀌었고 API 동작 증거가 없다`
  - 예(틀림): `완료 게이트: vmc-harness evidence api로 /orders를 호출한 뒤 다시 종료하세요`
- 작업 중 압박 신호: 예측·예산·실측 숫자(P5 — `core/inject`가 거른다)
- 사람 이름을 주어로 한 결함 서술(결함의 주어는 도구·과정)

## 이유

절차를 박으면 모델이 거기에 매여 일하고, 모델이 좋아져 더 나은 방법을 찾아도 그 이득을 못 누린다. 출력 형식과 안전선만 기계로 강제하고, 품질은 결과로 본다.

## 검사

기계 검사는 없다(문구의 절차 여부를 기계로 판정하면 오탐이 난다). 커널 문구를 바꾸면 회귀 세트(`vmc-harness eval`, spec 11)로 결과를 비교한다 — 기준선보다 같거나 나아야 릴리스한다.
