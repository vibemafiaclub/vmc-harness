# VMC 하네스 커널 원칙

이 문서는 하네스 엔진(L0)과 함께 배포된다. 에이전트는 읽기만 한다 — 엔진 폴더 쓰기는 훅이 막는다. 바뀌는 길은 VMC 릴리스뿐이다.

## 목표

사람은 개발 지시만 한다. 하네스는 이 팀의 실제 작업 기록에서 배워 안전장치를 스스로 만들고, 실측으로 효과 없는 것은 스스로 걷어낸다. 막을 것은 말(지침)이 아니라 구조와 게이트로 막는다.

## 원칙

- **P1 유도 수단의 우선순위는 구조 > 게이트 > 규칙 > 카드다.** 구조는 틀릴 수 없게 하고, 게이트는 틀리면 막고, 규칙은 매 세션 읽히고, 카드는 상황마다 답이 다른 판단을 담는다. 규칙·카드로 하는 조치는 더 위 수단이 아닌 이유(`why_not_higher`, 200자 이하)가 있어야 한다 — 비면 메타 게이트가 거부한다. 기계로 판정할 수 없는 취향(문체·디자인 감각)은 게이트가 되지 않는다.
- **P2 finding은 사람의 명시적 행동에서만 생긴다.** "그냥 진행"(헛막기), 조치·작업 커밋의 revert, `why` 후보 중 사람이 지목한 원인, 승인 카드 거절, 패널 버튼이 전부다. 해석이 필요한 신호는 후보·참고 지표다. LLM이 해석한 학습 후보는 브레인 카드 밖(규칙·게이트)으로 가지 못한다. 진단 제안도 finding이 아니다 — 진단 자동 반영의 근거는 모델이 낸 칸(사람 규칙 충돌·방향·신호)과 백테스트 숫자를 코드가 검사한 결과다.
- **P3 게이트의 근거는 사람의 명시 요청과 기계 사실뿐이다.** 명시 요청은 사람이 한 말 그대로의 범위와 원문·출처로 남는다. 기계 사실은 읽어 온 명령과 함께 남고, 값이 바뀌면 규칙도 바뀐다. 게이트를 풀거나 지우는 근거는 헛막기 finding이다. 예외로 진단 자동 반영(`diagnosis_auto`)이 있다: 기계 검사(사람 규칙 충돌 없음·조이기만·커널/외부 발송/결제/삭제에 닿지 않음·gate는 백테스트에서 실제 문제를 잡은 변경이 있음)를 전부 통과한 제안만 시험 조치로 들어간다. 게이트 풀기·보호 영역 해제·훅 제거는 자동 반영되지 않는다.
- **P4 사람이 시키지 않은 일로는 승인 요청이 생기지 않는다.** 하네스가 스스로 시작한 일에서 나온 것은 제안으로 쌓이고, 사람이 그 영역을 작업할 때 보인다. 알림은 승인 요청이 아니다 — 무시해도 되고 기본값이 있다.
- **P5 작업 중 에이전트에게 들어오는 메시지는 허용 목록뿐이다.** 안전 게이트 위반, 종료 시점의 빠진 증거, 선언 범위 밖 첫 편집 직전 PM 의견 1회. 예측·예산·실측 숫자는 작업 중에 보이지 않는다. 착수 시점의 과거 실측·카드는 허용된다. 사람이 방금 쓴 프로젝트 용어의 뜻(같은 세션 같은 용어 1회)도 허용된다 — 사람 말을 풀어 줄 뿐 압박이 아니다.
- **P6 판단은 모델이 한다.** 하네스가 LLM에 주는 것은 목표·참고할 수 있는 것(도구 포함)·제약·출력 형식이고, 강제하는 것은 출력 형식과 안전선이다. 품질은 결과(정답지·수용률·회귀 세트)로 잰다. 게이트 메시지는 무엇이 빠졌는지·무엇을 어겼는지만 담는다.
- **P7 판정은 스크립트가 숫자로 한다.** 조치를 만든 쪽이 그 조치를 채점하지 않는다. 존속·원복은 장부 숫자로 정해진다. 모델의 판단(충돌·방향)은 발견이고, 반영 여부는 코드가 칸과 숫자로 정한다 — 칸이 비면 반영하지 않는다. 자동 반영 조치는 부작용 지표(그 게이트의 헛막기·반박 비율, 반영 뒤 새 테스트 실패, 근거 신호가 줄지 않음)를 코드가 세어 원복한다. LLM 해석만으로 원복하지 않는다.
- **P8 안전 장치와 편의 장치는 다르게 실패한다.** 안전 장치(DB 안전장치·보호 영역·검증물 변조 금지·완료 게이트)는 확인할 수 없으면 막는다. 편의 장치(PM·과설계 판정·카드 검색·렌더링)는 가벼움 예산을 넘으면 비싼 것부터 빠지고, 오류면 통과한다.
- **P9 고객 데이터는 고객 PC·레포 밖으로 나가지 않는다.** VMC 서버로 가는 작업 데이터는 0바이트(라이선스·버전·잠금만)다. 팀 장부에는 숫자·상태·해시만 있고 원문·코드 조각·비밀값은 없다. 비밀값은 대화가 아니라 터미널 직접 입력(`vmc-harness db-credential`)으로만 받는다.

## 사람이 개입하는 경우 — 세 가지

1. 자동 롤백으로 되돌릴 수 없는 운영 반영: 배포(main 머지·push가 배포인 팀), 운영 DB에 SQL 적용, 데이터에 부작용이 남는 쓰기 경로 변경
2. 안전 경계를 넓히는 일: 보호 영역 코드 변경, 보호 영역 목록 줄이기, 느슨한 프로파일
3. 사람만 가진 정보·업무 결정: 처음 1회 자격 증명, QA의 사람 결정, 요구사항 판단, 게이트가 잘못 막았을 때 "그냥 진행"

새 사람 승인 게이트는 이 셋 중 어디에 해당하는지가 적혀 있어야 한다(빈칸은 메타 게이트가 거부). 게이트·규칙 관리, 조치 존속·원복, 업데이트는 사람 몫이 아니다.

## 하네스 도구

- `vmc-harness evidence` — 화면·API 호출·테스트 실행을 실제 동작 증거로 남긴다
- `vmc-harness impact <파일|파일:심볼>` — 바뀐 코드의 호출처·영향 페이지
- `vmc-harness db query "<SELECT>"` — 개발 DB 읽기 전용 조회(등록된 프로젝트). 다른 경로의 DB 직접 접속은 막힌다
- `vmc-harness why <파일|작업 id>` — 그 작업·파일에 영향을 준 규칙·카드·게이트·자동 변경
- 브레인 MCP `search_cards` — 이 팀·프로젝트를 넘어 쌓인 판단 카드
